# ADR — журнал архитектурных решений

**Что это.** ADR (Architecture Decision Record) — короткий документ на **одно** архитектурное решение: контекст → что решили → почему → последствия. Лежат здесь, в `docs/adr/`, со **сквозной нумерацией** (`0001-…`, `0002-…`). Шаблон — [`0000-template.md`](0000-template.md).

**Зачем.** «Почему» проекта нельзя держать в комментариях к задачам и переписке — оно теряется. ADR — дистиллят решения: агент читает его **перед** правкой и не «чинит» то, что было выбрано сознательно. Дёшев по токенам: одно решение прочитать проще, чем реконструировать его из истории коммитов.

## Когда заводить ADR — когда сошлись 3 условия

1. решение **дорого откатить** (влияет на структуру, данные, контракты);
2. без контекста оно **выглядит странно** (кто-то потом захочет «починить»);
3. были **реальные альтернативы** и выбор — осознанный трейдофф.

Если хотя бы одно условие не выполнено — ADR не нужен, хватит `comment` на задаче в Atlas.

## Правила ведения

- **Нумерация сквозная**, файл — `NNNN-краткий-слаг.md` (`0001-operating-model-foundamentals.md`).
- **Не редактировать задним числом.** Принятое решение — исторический факт. Если решение отменено новым — старому ставим `Статус: superseded` (со ссылкой на новое ADR), а не переписываем его.
- **«Схлопывание».** Когда цепочка `superseded` разрослась, допустимо свести её к одному ADR с текущим состоянием — ради экономии контекста агента. Прежние помечаем как схлопнутые.
- **Статусы:** `proposed` → `accepted` → (`superseded` / `deprecated`).

## Что НЕ идёт в ADR

- **состояние** (ветка/worktree, стадия) — это тег/поле задачи в Atlas;
- **ход работы / handoff** — `comment` на задаче в Atlas;
- **черновой план реализации** — scratchpad, в `.gitignore`, в репо не коммитится.

Полная модель фиксации артефактов (4 слоя) — в `ai-ecosystem-core/AGENT-OPERATING-MODEL.md`, раздел «Модель фиксации артефактов».
